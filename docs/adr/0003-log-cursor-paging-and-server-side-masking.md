# ADR 0003 — 로그는 커서로 페이징하고, 마스킹은 서버에서만 한다

- 상태: Superseded by 0006
- 날짜: 2026-08-13
- 결정자: @xenx96
- 관련: 이슈 [#16](https://github.com/xenx96/k8s-dashboard/issues/16), [#7](https://github.com/xenx96/k8s-dashboard/issues/7) · README §10 보안 원칙, §11 성능 원칙 · ADR 0002 · ADR 0006

## 배경

Logs Explorer는 두 가지를 동시에 만족해야 합니다.

1. **대량 결과를 안전하게 넘긴다.** 장애 구간의 로그는 수만 줄이 나옵니다. 브라우저에 한 번에
   적재할 수 없고, 페이지를 넘길 때 줄이 빠지거나 겹치면 조사 자체가 틀어집니다.
2. **민감정보가 새지 않는다.** 로그 본문에는 토큰·비밀번호·시크릿·카드번호가 섞입니다.
   이슈 #16 완료 기준은 "마스킹 정책이 API와 UI 모두에 적용됨"입니다.

두 요구가 흔히 잘못 구현되는 방식이 있습니다.

- `offset`/`page` 기반 페이징 — 로그는 계속 들어오므로 다음 페이지를 요청하는 사이 앞쪽에
  새 줄이 끼어들고, 경계가 밀려 **중복과 누락**이 동시에 생깁니다.
- 원문을 내려보내고 UI에서 정규식으로 가리기 — 네트워크·브라우저 메모리·개발자 도구·복사
  어디에서든 원문이 노출됩니다. "UI에도 적용"을 "UI에서 수행"으로 잘못 읽은 결과입니다.

## 결정

### 1. 커서 페이징 — offset을 쓰지 않는다

- 커서는 **(timestamp, id) 복합키**를 불투명 문자열로 인코딩한 값입니다. 클라이언트는 해석하지 않습니다.
- 정렬은 최신 우선(`t DESC, id DESC`)이며 커서는 이 정렬을 전제로 "그 다음"을 가리킵니다.
- **로그 id는 충돌이 불가능해야 합니다.** 같은 밀리초에 여러 줄이 들어오므로 timestamp만으로는
  부족하고, id가 겹치면 커서가 잘못된 위치를 가리켜 중복이 발생합니다.
  (mock 구현에서 실제로 이 버그를 만들고 검증 과정에서 잡았습니다 — 800줄 중 4줄 중복.)
- 커서가 가리키던 줄이 사라졌으면(보존기간 만료) timestamp 기준으로 이어붙입니다. 조용히
  처음으로 되돌아가지 않습니다.
- **결과 상한은 서버가 강제합니다.** 상한에 걸리면 응답에 `truncated: true`로 명시하고
  화면이 "잘렸다"고 알립니다. 조용히 자르지 않습니다.

### 2. 마스킹은 서버에서만 한다

- API 응답의 `message`는 **이미 가려진 문자열**입니다. 원문은 응답에 들어가지 않습니다.
- 무엇이 가려졌는지는 `masked: MaskedSpan[]`(위치·길이·종류)로 별도 전달합니다.
  UI는 이 정보로 표시만 하고, **원문을 복원할 수 없습니다.**
- UI는 원문 조회·복사 경로를 제공하지 않습니다. 복사는 화면에 보이는(=가려진) 내용만 됩니다.
- "API와 UI 모두에 적용"은 이렇게 읽습니다 — API가 가리고, UI는 가려졌다는 사실을 사용자에게
  **보이게** 합니다. UI가 가리는 것이 아닙니다.

### 3. 히스토그램과 facet은 레벨 필터 이전 집합으로 계산한다

레벨 필터까지 반영하면 꺼져 있는 레벨의 카운트가 항상 0으로 보여 필터가 쓸모없어집니다.
시간·Scope·Workload·Pod·Container·검색어까지만 적용한 집합으로 세고, 레벨은 줄 목록에만 적용합니다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| `offset`/`page` 페이징 | 실시간으로 들어오는 로그에서 중복·누락이 구조적으로 발생한다. 이슈 #16 완료 기준을 만족할 수 없다. |
| 시간만으로 커서 구성 (`t < lastT`) | 같은 밀리초에 여러 줄이 있으면 경계에서 줄이 통째로 사라진다. |
| 전체 결과를 한 번에 내려주고 클라이언트에서 페이징 | 브라우저 메모리와 전송량이 터진다. README §11 위배. |
| 원문을 내려주고 UI에서 마스킹 | 네트워크·devtools·메모리 어디서든 원문이 보인다. 마스킹이 아니라 "가린 척"이다. |
| 권한 있는 사용자에게 원문 노출 옵션 | MVP 범위 밖. 필요해지면 서버에서 별도 감사 로그를 남기는 경로로 설계하고 ADR을 새로 쓴다. |
| 무한 스크롤 대신 페이지 번호 UI | 로그 조사 동선과 맞지 않는다. 시간축을 따라 내려가는 흐름이 자연스럽다. |

## 결과

**좋아지는 것**

- 페이지 경계가 안정적이다. 8페이지(800줄) 연속 수집에서 중복 0, 누락 0을 테스트로 확인했다.
- 브라우저 적재량이 상한을 갖는다. 100줄 단위 커서 페이지 + 라인 가상 스크롤로,
  1,000줄을 불러와도 DOM에는 40줄 남짓만 존재한다.
- 마스킹 정책의 책임 위치가 하나다. 클라이언트가 새 화면을 만들어도 정책이 새지 않는다.
- 사용자가 "무엇이 가려졌는지"를 안다. 그냥 사라진 값과 마스킹된 값이 구분된다.

**감수하는 것**

- 커서는 임의 위치 점프를 못 한다. "10페이지로 바로" 같은 기능은 불가능하다 —
  로그 조사에서 필요한 적이 없는 기능이라 감수한다.
- 서버가 마스킹 규칙을 유지해야 한다. 새 형식의 시크릿이 나오면 서버를 고쳐야 하고,
  그 전까지 로그에 남는다. 수집 단계 마스킹은 별도 과제다.
- 펼침은 한 번에 한 줄만 허용한다. 가변 높이가 여럿이면 가상 스크롤 오프셋이 추측이 되고
  스크롤이 튄다. 정보 밀도보다 스크롤 안정성을 택했다.

## 구현 노트 — 실 Quickwit 어댑터의 커서 (2026-08-14, #7)

`apps/api/internal/datasource/quickwit`에서 이 결정을 실제 백엔드에 적용하며
커서 형식을 한 단계 구체화했다.

**커서 = (경계 timestamp, 경계에서 이미 내려간 문서 id 집합).**
Quickwit ES 호환 API의 `search_after`는 정렬 키가 timestamp 하나뿐이면
같은 밀리초에 몰린 문서를 건너뛰거나 중복시킨다. 유일한 tie-breaker 필드를
인덱스에 강제할 수 없어서, 대신 다음 페이지를 `timestamp <= 경계`(경계 포함)로
질의하고 **경계 timestamp에서 이미 내려간 id를 서버가 걸러낸다.**

- 다음 페이지 요청 크기는 `size + len(경계 id)`다. 경계 문서를 다시 받는 비용을
  선지불하고 중복을 0으로 만든다.
- 경계 id가 이전 커서와 같은 timestamp에서 이어지면 목록을 이어받는다.
  같은 밀리초의 문서가 페이지 크기보다 많아도 전진이 보장된다.
- 경계 id는 512개에서 자른다(`maxBoundaryIDs`). 같은 밀리초에 그 이상 몰리는
  극단에서는 중복 가능성을 감수한다 — 커서가 무한히 자라는 것보다 낫다.
- 문서 id는 Quickwit `_id`를 쓰고, 없으면 (timestamp, pod, container, message)의
  결정적 해시로 만든다. 재조회해도 같은 id가 나와야 경계 걸러내기가 성립한다.

검증은 `TestCursorPagingHasNoDuplicatesOrGaps`(900건, 7건씩 같은 밀리초 공유)와
`TestOffsetPagingIsNeverUsed`(어떤 요청 본문에도 `from`/`start_offset` 없음)가 한다.
